# 饮食记录与报表分析设计

设计日期：2026-10-02。状态：设计完成，功能未实现。本文是两个新增需求的实施入口；当前运行能力仍以代码和 README 为准。

## 1．结论与范围

建议先实现本地饮食识别和确定性的收支分析，再接入可选 LLM，生成更自然的总结和行动建议。

- 独立增加「饮食」菜单，按日期展示早餐、午餐、晚餐、加餐及餐次待确认记录，支持店名、菜品和人工纠正。
- 周报、月报增加「收支分析」区域：本地展示事实和提醒，用户点击「生成 AI 总结」后才调用已配置的供应商。
- 金额、占比、比较、异常触发和预算候选值全部在本地计算。LLM 只解释事实、组织建议，不负责算账或修改数据。
- 饮食模块不依赖 LLM。没有模型配置或网络连接时，两个模块的本地能力仍可使用。
- “理财建议”本轮定义为消费复盘、开支提醒和下一周期预算建议。证券推荐、收益预测、资产配置、账户余额和完整预算管理不在本轮范围。

账单能证明消费，通常不能证明实际用餐人、用餐时间或完整菜品。页面统一标注「根据账单推断」；无证据时写「菜品未提供」「店名未提供」，不得补写“包子、豆浆”等猜测。

## 3．实施前置决策

### 3.1 数据库与项目范围

数据库路线已由用户确认：默认和日常运行均使用现有 H2，不使用 MySQL，不自动迁移或初始化。项目规范与启动配置已统一；测试夹具在隔离内存 H2 中显式初始化，不接触个人数据。

饮食和 AI 分析仍是未实施的增量设计。后续涉及表结构或历史数据的变更必须单独明确授权，先同步项目范围规范和人工执行方案，不通过应用启动自动实施。

### 3.2 先保证正式入账边界

按已有 P0 方案增加暂存交易模型：解析写暂存，确认时重新去重，在事务中写正式交易并确认批次。先只读盘点历史未确认批次和预写交易，形成迁移清单后再按明确授权迁移，不直接删除历史记录。

饮食正式记录只能由已确认交易产生；解析阶段可用同一个纯规则函数预览建议，但不得提前写饮食表。LLM 不进入导入确认事务。

## 4．饮食模块

### 4.1 页面与用户流程

「饮食」位于「报表」「分类管理」旁边，默认显示本月，支持日期区间、餐次和待确认筛选。

按日分组示例，全部为虚构测试数据：

```text
2026-09-15
早餐  08:12  示例早餐店  包子、豆浆  ¥12.00  根据账单推断
午餐  12:18  示例面馆    菜品未提供  ¥28.00  根据账单推断
晚餐  暂无可识别账单
待确认  日期精度账单：示例餐馆，餐次未知
```

- 导入确认后提示「已识别饮食记录 N 条，待确认 M 条」；不增加新的强制确认步骤。
- 高置信度且餐次可确定的餐饮自动进入日列表；中等置信度或餐次待确认的记录只进入待确认区；低置信度不展示、不创建饮食记录。
- 每条展示店名、账单中可提取的菜品、金额、餐次、推断依据，支持跳转关联交易。
- 支持修改日期、餐次、店名、菜品，以及「不是饮食」排除；人工修正不改原交易金额或原摘要。
- 正式日列表不混入尚未确认的候选。空白显示「暂无可识别账单」，不显示「没吃早餐」。
- 饮食金额是关联消费金额，不能等同于个人实际吃掉的金额；同餐多笔可并列，不自动合并或拆分金额。

### 4.2 判断顺序与证据强度

严格按下列顺序执行，时间和金额不能单独构成餐饮证据：

1. **有效交易门槛**：只处理已确认、`EXPENSE`、金额大于零且非「忽略」的交易。收入、还款、转账等中性交易不进入饮食模块。
2. **人工决定优先**：保留人工确认、修正和排除。人工归入明确非餐饮分类的交易，不自动转成饮食；需要用户手动确认。
3. **排除证据优先**：便利店、超市、生鲜、杂货、充值、礼品卡、代购及混合购物摘要不自动当作一餐。仅有“美团”“饿了么”等平台名也不直接确认餐饮。
4. **正向证据**：明确餐饮商户映射或明确即食菜品，且无排除／冲突证据，评为 `HIGH`；餐饮分类但商户不明、平台订单可能是餐饮、餐饮与非餐饮信息冲突，评为 `MEDIUM`；其余为 `LOW`。
5. **餐次判断**：只有餐饮门槛通过，才用可靠时间分餐次；菜品与时间冲突时保留餐饮记录，餐次设为待确认。

`HIGH／MEDIUM／LOW` 是确定性证据等级，不是“准确率 90%”之类概率。记录规则 ID、匹配字段、原因码和规则版本，便于解释与重算。

状态映射固定为：HIGH 且餐次已确定 → AUTO_ACCEPTED；MEDIUM 或 UNASSIGNED → PENDING_REVIEW；用户确认 → CONFIRMED；用户排除或自动规则失效 → EXCLUDED。LOW 不新建记录，已有自动记录变 LOW 时按规则失效处理。

识别规则先维护在版本控制的本地规则文件中，不新增完整规则管理界面。商户规则包含来源、精确商户名或经核对的关键词、饮食类型及优先级；强商户匹配优先于宽泛摘要匹配，排除规则优先于正向规则。“商城、充值、商贸”等不能仅靠单个词决定所有交易。

超市明确含即食菜品的订单进入待确认区；同时含洗衣液等非食品时不自动确认整笔为一餐。无法拆分食品金额时保留整笔账单金额，并明确标注，不估算食品部分。

### 4.3 餐次、时间和内容提取

默认时区 `Asia/Shanghai`，规则 v1 的半开时间区间：

| 餐次 | 时间范围 | 限制 |
| --- | --- | --- |
| `BREAKFAST` 早餐 | `[05:00, 10:30)` | 必须先通过餐饮识别 |
| `LUNCH` 午餐 | `[10:30, 14:30)` | 必须先通过餐饮识别 |
| `DINNER` 晚餐 | `[17:00, 21:00)` | 必须先通过餐饮识别 |
| `SNACK` 加餐 | 其他时间 | 仅明确零食、饮品、小食；不把全天其他餐饮都强行归为加餐 |
| `UNASSIGNED` 餐次待确认 | 无可靠时间或未命中以上规则 | 允许人工选择餐次 |

新增交易 `time_precision`：`DATETIME／DATE／UNKNOWN`。解析器从原始时间字段确定精度；`ParserSupport.date` 目前会把日期补成零点，零点不能用于判定夜宵。历史数据无法可靠还原精度时填 `UNKNOWN`；招行已有日期精度记录不直接按零点分餐。

饮品专门店优先显示为加餐；早餐店凌晨付款、晚间摘要“明日早餐”等冲突设 `UNASSIGNED`。支付日期作为默认记录日期，提前下单或多人代买由用户修正，系统不声称识别了实际用餐时间。

店名取值：经核对的商户映射名称 → 明确的交易对方 → 摘要中明确出现的店名 → 空值。平台名与店名分开；泛化对方如“商户”“二维码收款”不补成店名。菜品仅保留原摘要中可证明的菜品片段，清理订单号等噪声；原文没有菜品则为空，禁止根据店名推菜单。

### 4.4 数据模型与一致性

新增 `meal_record`，一笔正式交易最多一条记录，以 `transaction_id` 唯一约束保证幂等。多个交易属于同日同餐时在查询层分组，不创建复杂的多表用餐事件。

| 字段 | 类型／约束 | 用途 |
| --- | --- | --- |
| `id` | BIGINT 主键 | 饮食记录 ID |
| `transaction_id` | BIGINT，唯一、外键 | 追溯正式交易；金额和来源通过关联读取，不复制 |
| `meal_date` | DATE，非空 | 默认付款日期，可人工修正 |
| `meal_type` | VARCHAR(16) | 五种餐次枚举 |
| `merchant_name` | VARCHAR(255)，可空 | 可证明或人工填写的店名 |
| `food_items` | VARCHAR(1000)，可空 | 菜品文本，不保存原始账单 JSON |
| `status` | VARCHAR(16) | `AUTO_ACCEPTED／PENDING_REVIEW／CONFIRMED／EXCLUDED` |
| `origin` | VARCHAR(16) | `RULE／MANUAL`，人工操作后为 MANUAL |
| `confidence` | VARCHAR(16) | `HIGH／MEDIUM`，LOW 不入表；人工确认仍保留原推断等级 |
| `reason_codes` | TEXT，JSON 编码 | 原因码、规则 ID、证据字段；不复制完整敏感原文 |
| `rule_version` | VARCHAR(32) | 识别规则版本 |
| `version` | BIGINT | 乐观锁，防止编辑与重算互相覆盖 |
| `created_at／updated_at` | 时间 | 审计与排序 |

索引：唯一 `transaction_id`；组合 `(meal_date, status, meal_type)`。新交易字段和表须另行确认 H2 结构变更方案及执行授权，不在启动时自动迁移；字段注释、枚举说明与 Javadoc 同步补全。

- 导入确认事务中仅对最终成功入账的交易执行规则并写记录；规则异常使该次事务回滚，避免部分入账。不存在模型调用或文件识别操作。
- `EXCLUDED` 保留为排除标记，不物理删除，否则重算会把用户排除的消费重新生成。
- 批量重算只覆盖 `origin=RULE`，人工记录不覆盖；原自动记录不再符合规则时标记排除并记录原因，不能继续显示旧结论。
- 分类修改、删除或重新分类后，对受影响交易执行同一协调逻辑。关联交易变为未确认、非支出或「忽略」时，即使人工记录也先从日列表隐藏，保留人工内容并提示冲突。
- 历史补生成提供只读预览数量，用户选择日期范围后执行；按 ID 分块、逐块事务、重复执行幂等，禁止重导原账单或覆盖人工结果。
- 本轮不实现完整退款配对。明确标记为取消／全额退款的订单不自动确认饮食；信息不足时只提示消费事实待核实，不认定实际用餐或计算净饮食支出。

### 4.5 API 契约

| 接口 | 行为与关键校验 |
| --- | --- |
| `GET /api/meals?from=&to=&status=&mealType=&page=&size=` | 按日期倒序、交易时间、ID 稳定排序；日期含首尾，查询转换为半开区间；默认 size=50，最大 200 |
| `GET /api/meals/{id}` | 返回饮食 DTO、推断依据和必要交易字段，不返回账户或原始 JSON |
| `PATCH /api/meals/{id}` | 修改日期／餐次／店名／菜品／确认或排除；携带 version，冲突返回 409 |
| `GET /api/meals/rebuild-preview?from=&to=` | 返回新增、重算、人工跳过、待确认预计数量，不写数据 |
| `POST /api/meals/rebuild` | 明确范围后分块补生成，返回实际数量及原因汇总 |

非法日期、未知餐次、超长文本返回 400，不存在返回 404；PATCH 不接受金额、账户、交易方向修改。默认单次补生成不超过一年，大于一年拆分执行，不扫描其他账单目录。

PATCH 只允许用户将记录设为 CONFIRMED 或 EXCLUDED，不能伪造 AUTO_ACCEPTED、origin 或 confidence。用户确认 UNASSIGNED 时必须填写餐次；非空白记录必须有可用日期。列表和重算入口继续限定关联批次已确认，无法通过修改状态绕过有效交易门槛。

## 5．周报与月报收支分析

### 5.1 页面行为

报表图表下增加「收支分析」，在周／月模式显示：周期总结、值得关注的变化、下一周行动、下月预算候选和数据局限。周报同时给下一周行动与下月方向；月报给所选月份之后一个月的建议，例如 2026 年 9 月月报对应 10 月。

切换周期立即展示本地分析，读取匹配缓存；未开启 AI 时显示配置状态。用户点击「生成 AI 总结」才发起外部请求，不因刷新、筛选或切换日期自动产生付费调用。生成中可继续使用交易和报表；切换周期后旧响应不能覆盖新周期结果。

AI 文案与本地事实分开标识，展示生成时间、模型及数据快照状态。「刷新分析」先重算本地事实，输入未变化且已有成功结果时复用缓存。本轮不做全文报告下载或对话式财务助手。

### 5.2 周期、数据质量与统计口径

- 复用统一的 `ReportPeriodResolver`：周一到下周一、自然月第一天到下月第一天，内部为 `[from, to)`；UI 显示含首尾日期。周界不能用趋势图中裁剪到月内的 week1／week2 代替。
- 正式、已确认、非「忽略」交易才参与统计；`NEUTRAL` 不计收入或支出。保留未分类金额及占比。
- 所有金额使用 `BigDecimal／DECIMAL`；百分比除零返回空值，展示“无法比较”；后端保留 4 位金额精度，展示才保留 2 位。
- 账单导入不能证明覆盖全部账户或完整月份。增加周期完整性说明 `UNKNOWN／PARTIAL／USER_CONFIRMED`，默认 UNKNOWN，供用户在分析区域标记“该周期主要收支已导齐”或“仍有缺失”；这是数据覆盖声明，不是系统证明。
- 未分类占比超过 20% 时提示先完善分类，降低分类建议强度；此值为产品初始规则，不是财务标准。
- 所选周期未结束时标记“进行中”，只比较同等已过天数，不拿月初支出与整月直接比较。当前日数据可能不完整，默认比较截至昨日，今日事实单独展示；用户晚些导入历史账单后重新计算。
- 完整历史月展示总额变化，并增加日均变化修正 28／30／31 天差异。进行中月份比较前月相同日序，天数取两者可比天数的较小值；周比较相同已过日数。
- 历史对比不足时不给增长结论；用户声明缺失的周期不参与基准。UNKNOWN 只提供“已导入账单比较”，不判定完整收支恶化或给确定储蓄目标。
- 退款净额、跨支付平台与银行卡的同笔消费尚无统一核验时，在局限中说明。新模块不自行进行跨来源模糊去重，也不静默改变现有报表统计。

新增完整性声明表 `report_period_coverage`：`period_type`、`period_start` 唯一，`status`、`updated_at`；支持 `PATCH /api/reports/coverage`，只允许 WEEK／MONTH 的规范化周期。声明变化影响分析快照。实现时补齐零交易但用户声明完整的周期，不能把零消费自动当作缺数据。

`GET /api/reports/insights` 的 DTO 至少包括 period、from、to、asOf、coverage、facts、alerts、budgetCandidates、limitations 和 aiCache。每项 fact 包含稳定 ID、度量类型、十进制字符串 value、单位、适用区间和可比区间；alert 只引用现有 fact ID，budgetCandidate 包含目标月份、分类代码、参考值、候选值、假设节省额和计算规则。非法周期返回 400，未来周期返回空事实与说明，不调用模型。

### 5.3 本地事实与提醒规则 v1

先产生有稳定 ID 的事实，再触发提醒；每条提醒包含规则版本、触发阈值、事实 ID 和对比区间。下表数值是待用户试用调整的产品默认值，不构成普适的“合理开支标准”。

| 提醒 | 规则 | 输出边界 |
| --- | --- | --- |
| 支出较上期增加 | 可比窗口支出增长至少 20%，且增加至少周 ¥50／月 ¥200 | 两个门槛同时命中；前期为零时只报告新增金额，不生成无限增长率 |
| 分类变化突出 | 同等窗口分类金额增长至少 30%，且增加至少周 ¥50／月 ¥200 | 房租、医疗、保险等只提醒核对原因，不自动建议削减 |
| 分类占比较高 | 某分类占支出至少 30%，且金额至少周 ¥100／月 ¥300 | 称“占比较高”，无历史或用户预算时不称“超支” |
| 频繁小额消费 | 同分类一周期至少 10 笔，每笔不超过 ¥30，累计至少 ¥150 | 不推断都是可削减消费；展示频次与累计值 |
| 已导入收支为负 | 本周期 expense > income | 仅表述账单支出超过账单收入；无完整收入声明不说“财务危机” |
| 分类质量不足 | 未分类支出占比 >20% | 优先建议完善分类，不把“未分类”当成消费习惯 |

周基准取此前最多 4 个可用完整自然周，月基准取此前最多 3 个可用完整自然月；月日均基准按各月实际天数计算。只有用户标记完整且至少 2 个历史周期，才启用个性化稳定基准和量化预算候选；否则只给方向与本期可核对事实。

### 5.4 下月建议如何生成

建议按优先级限定最多 3 项，每项必须说明依据、行动和可量化的核对方法：

- 先核对新增的大额或一次性支出、缺失收入和未分类项，避免为正常医疗或年度保险开支制造“过度消费”结论。
- 对用户认可可调整的餐饮、娱乐等分类，在足够完整历史月份下，以近 3 个完整月金额中位数作为参考。候选值可为参考值的 90%，同时展示“假设减少 10%”，不得强制套用到刚性分类。
- 周报可以使用完整历史月生成下月候选；只有周数据时不把一周乘 4 当作确定月预算。
- 示例：历史三个完整月餐饮为 ¥900、¥1,000、¥1,200，参考中位数 ¥1,000，候选 ¥900，假设节省 ¥100。它是建议值，需用户自行采纳，不写入预算或交易。
- 历史不足、收入未覆盖或周期声明未知时，仅输出“先导齐账单”“核对餐饮频次”等建议，不推断可投资金额、资产余额、风险偏好或投资回报。

## 6．LLM 接入方案

### 6.1 是否需要、先接哪一家

消费识别、异常提醒和量化候选不需要 LLM；自然语言复盘和因数据情境组织行动建议适合接入。建议首版实现一个可替换的 `ReportAdviceClient`，默认提供 `NONE`，先接通 DeepSeek，再按同一业务契约接 GPT，不同时调用多个模型投票。

DeepSeek 官方文档确认提供 OpenAI 兼容接口，这适合当前小型 Java 项目；这不等于所有结构化输出参数完全一致，也不是对质量或价格的实测比较。[DeepSeek 官方接入说明](https://api-docs.deepseek.com/) 。

OpenAI 提供 JSON Schema 结构化输出；普通 JSON 模式只保证 JSON 格式，不能代替业务 schema 校验。GPT 适配器优先使用所选模型支持的结构化输出，仍做本地验证。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 。

本次 DeepSeek JSON 模式与 Chat Completions 详细页面抓取超时，结构化输出字段和所选模型能力列为接入前待核对项，不据搜索摘要锁定请求参数。不在文档固化易变化的模型名、价格或“最便宜”结论。首家是否最终选 DeepSeek，可在合成样本试测后调整。

复用现有 Spring HTTP 客户端和 Jackson；首版采用普通 HTTP 请求，业务侧统一输入输出，两家供应商仅保留必要的协议差异。不新增 Spring AI、LangChain、RAG 或工具执行能力。

### 6.2 输入、输出和事实校验

仅发送白名单汇总：分析起止日期、分类代码、汇总金额与次数、比较窗口、提醒 facts、可用预算候选、完整性状态和局限。分类名采用系统已知展示映射；自定义分类转换为本地匿名代码，避免自定义名称包含姓名、地址或指令。

不发送账单文件、原始 JSON、流水号、账户、收款人、店名、菜品、交易摘要或单笔明细。饮食模块的敏感内容不进入报表模型输入。聚合仍属于财务数据，首次启用供应商时展示发送范围，用户明确开启后生效；此次设计工作不调用真实分析 API。

模型内部输出契约示例，字段只用于解释本地 facts，示例不是供应商请求 body：

```json
{
  "summary": {
    "text": "餐饮是本周期值得复盘的开支，可先核对就餐频次。",
    "evidence_ids": ["category_food_share"]
  },
  "observations": [
    {
      "title": "餐饮占比较高",
      "text": "建议查看明细，确认是否有聚餐或代付款。",
      "evidence_ids": ["category_food_share"]
    }
  ],
  "actions": [
    {
      "title": "复核餐饮开支",
      "text": "核对大额消费与经常出现的小额消费，再选择调整空间。",
      "evidence_ids": ["category_food_share"],
      "budget_candidate_id": null
    }
  ],
  "limitations": ["仅依据已导入账单。"]
}
```

后端用 Jackson＋Validation 验证字段、长度、枚举和集合上限，拒绝不存在的 evidence ID、越权结论和未知预算候选。最多 3 条观察与 3 条行动。数字和预算由后端依据 facts／candidate ID 单独渲染；模型文本禁止新增金额、百分比、日期或收益率，发现数值性表述无法核对时整体降级，不把“可解析 JSON”当作准确建议。

summary、观察和行动必须有证据；没有可用事实时跳过模型，返回“暂无可分析的已确认账单”。空返回、截断、拒绝、结构错误或内容校验失败都不能展示为成功 AI 总结。提示词约束不代替后端校验，输出不允许生成可执行 SQL、HTML 或外部链接。

页面以文本节点渲染，不执行模型 Markdown／HTML；中文标点、中英文空格及 `--` 破折号在渲染层做确定性规范化，保留金额与合法英文标识。超长输出拒绝，不截掉证据后仍显示结论。

### 6.3 触发、缓存与失败处理

`POST /api/report-analyses`：参数为 WEEK／MONTH、date 和 provider；范围由后端解析，不接受客户端上传事实。返回 202＋analysisId 或 200＋匹配缓存。`GET /api/report-analyses/{id}` 查询 `RUNNING／SUCCEEDED／FAILED`，失败时同时返回可用本地分析与脱敏原因。`GET /api/reports/insights?period=&date=` 只计算本地事实和匹配缓存状态，不调用模型。

新增 `report_analysis`：`id`、唯一 `request_key`、period/from/to、`snapshot_hash`、provider/model、rule/prompt/schema 版本、status、execution_version、facts/result JSON、token 使用量、error_code、created/finished 时间。JSON 只保存脱敏汇总和最终可用结果，不保存密钥、原文 prompt、供应商完整错误或模型推理过程。

request_key 为规范化周期、快照、供应商、模型、提示词版本、规则版本和 schema 版本的组合哈希。快照来自本期与比较期的聚合事实、覆盖声明及预算候选；相同语义输入可复用。导入、分类修改、忽略状态和比较期历史补账导致输入变化时，旧结果标记过期。旧记录仅保留本地供追溯，不当作当前总结。

- 同 key 并发请求通过数据库唯一约束只创建一个任务；成功记录复用，失败记录允许用户点击重试。同一任务尚运行时不启动第二次。
- 本地单工作线程执行，队列最多 5 个；超额返回 429，本地分析仍可见。不引入消息队列或分布式任务平台。
- HTTP 连接超时建议 5 秒、总任务期限 60 秒；可确定安全重试的限流／服务错误最多重试一次，并计入总期限。鉴权失败、语义错误及不确定是否已计费的超时不自动重发。
- 应用重启将残留 RUNNING 标记为 FAILED／INTERRUPTED，用户主动重试。每次重试增加执行序号，只允许当前执行写结果，避免旧回调覆盖新结果。
- 周期变更时前端停止显示旧轮询结果；完成时核对 period、range 和 snapshot_hash。生成期间补入账单时，返回旧快照结果但标记过期，需要重新点击生成。
- 外部失败不影响账单确认、原报表、分类和饮食模块，展示本地规则总结；绝不把本地总结标为 AI 已生成。

### 6.4 配置、费用与隐私

配置：`app.ai.enabled=false`、provider、base-url、model、timeout、max-output-tokens；密钥仅从 `DEEPSEEK_API_KEY／OPENAI_API_KEY` 环境变量读取，不写页面、数据库、日志或仓库。页面最多展示配置是否可用，不显示密钥。供应商 host 由后端配置和允许列表控制，不让请求体传任意 URL。

建议每次汇总输入不超过 8,000 tokens、输出不超过 1,200 tokens；通过事实项上限与请求体大小限制前置控制，记录供应商返回的实际 token 使用量。按实施时官方价格计算合成样本单次成本，不预先声称成本；设置供应商账户额度和按日成功／尝试次数上限，重试也计入额度。

开启 AI 表示向所选供应商发送本次脱敏财务汇总，不能称“完全本地分析”。OpenAI 文档说明 API 数据默认不用于训练，但默认滥用监控仍可保留数据；`store=false` 不能视为零保留承诺。[OpenAI 数据控制](https://developers.openai.com/api/docs/guides/your-data) 。DeepSeek 数据条款在实际启用前单独核对，不套用 OpenAI 政策。未授权发送个人财务汇总时，只用虚构样本联调。

## 8．实施检查点与验收

| 检查点 | 依赖 | 交付与通过条件 |
| --- | --- | --- |
| P0 基础边界 | H2 路线已确认，结构／数据变更仍需独立授权 | 只读盘点后修复暂存／确认边界；重复／并发确认只入账一次；旧报表结果不变 |
| P1 饮食闭环 | P0 | 时间精度迁移、规则、日列表、待确认、人工修正、历史预览／重算；只生成餐饮且不覆盖人工数据 |
| P2 本地报表分析 | P0，可在 P1 后实施 | 周／月事实、完整性声明、提醒、历史比较、下月候选；关闭 AI 仍完整可用 |
| P3 AI 总结 | P2、供应商配置与汇总外发授权 | 先用合成样本接一家供应商，验证证据／数字校验、缓存、并发、失败降级；再按同契约扩展另一家 |

不创建或启动 Goal，不实施代码、schema、真实外发或 Git 提交。实现后运行相关自动化测试，并使用独立测试数据库和可重建的合成账单，禁止连接个人数据运行迁移测试。

核心验收用例：

| 输入／操作 | 预期结果 |
| --- | --- |
| 08:10，明确早餐店，摘要“包子豆浆” | 早餐；店名和菜品有原文依据；HIGH 自动展示 |
| 12:00，公交／药店／转账 | 不产生饮食记录，即使正好处于午餐时段 |
| 12:20，明确面馆，无菜品 | 午餐；显示面馆和“菜品未提供”，不猜具体面种 |
| 便利店洗衣液、超市混合购物、平台无商品描述 | 非饮食不记录；证据冲突或平台不明仅待确认，不进入正式日列表 |
| 只有日期的招行餐馆账单 | 可识别餐饮但餐次 UNASSIGNED，不按补齐的零点认定夜宵 |
| 10:30／14:30／17:00／21:00 边界 | 按半开区间唯一归属；无法确定正餐／加餐时餐次待确认 |
| 同日同餐多笔、重复导入、重复重算 | 多笔并列；每个 transaction_id 最多一条；金额无重复累加 |
| 待确认批次、失败批次 | 正式交易、饮食日列表和分析均不可见 |
| 人工排除后重算；人工改餐次后更新规则 | 排除持续生效，人工修正不被覆盖 |
| 餐饮改为忽略；删除餐饮分类；批量重分类 | 受影响饮食记录及时协调；分析快照变化；统计符合原报表口径 |
| 本周跨月、本月未结束、闰年 2 月、前期零支出 | 周范围完整；同等时间比较；天数正确；无除零或无限比例 |
| 无交易、无历史、缺失收入、未分类超过 20% | 明确局限，不生成无证据增长、资产或储蓄结论 |
| 完整历史月餐饮 900／1000／1200 | 本地中位数 1000，候选 900，假设节省 100；模型不能改数字 |
| 周报同时加载整月趋势、月报加载全年趋势 | AI 仅解释所选周／月，不能把图表全年金额当作当月开支 |
| 模型返回假金额、未知证据、空内容、超长内容、HTML、拒绝或截断 | 校验失败，显示本地总结；HTML 不执行；不标记 AI 成功 |
| 双击生成、并发请求、途中切周期／补账、进程重启 | 一个有效任务；结果周期不串；补账标记过期；中断可主动重试 |
| 401／429／5xx／超时、AI 未配置或关闭 | 报表与导入仍可用，错误脱敏；只按约定有限重试 |
| 自定义分类包含姓名、敏感文字或指令 | 模型请求仅含匿名分类代码，日志不含原文或 key |

运行验收必须覆盖真实 HTTP 路径：合成账单上传 → 确认 → 饮食列表／纠正 → 周月报 → 本地分析 → 模型成功和失败 → 查询结果及数据库计数。分别报告命令、监听状态、关键输入输出、前后数据结果；不能安全执行时标记「未验证」和阻塞项，不能以编译通过代替业务验收。

## 9．以后可增强的方向

- 待识别规则获得真实反馈后，可增加来源限定商户规则编辑和餐次时间调整；首版不提前建设规则平台。
- 饮食纠正沉淀为人工例外，后续经用户明确选择才扩展到相似商户，不自动学习宽泛关键词。
- 统一退款、跨来源重复消费与一次性开支标记后，再加强净支出分析和异常解释；不在本轮悄悄改变财务口径。
- 可评估本地模型，避免财务汇总外发；需要单独测试设备资源、延迟和总结质量，不为首版增加部署依赖。
- 以后增加用户预算目标和已采纳行动追踪，可检验建议是否有用；本轮候选值只展示，不建立完整预算子系统。
